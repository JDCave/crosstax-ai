# Feature Specification: CRS 自我证明表数据契约与抽取路径修订（HK/IRD）

**Feature Branch**: `001-crs-contract`

**Created**: 2026-11-04

**Status**: Draft

**Input**: User description: "以 IRD 官方发布的三份 HK CRS 自我证明表样本（个人版 / 实体版 / 控权人版）及其术语表为证据源，修订 crosstax-ai 的 CRS 数据契约（D3：把单值 jurisdiction_code + tin 改为 tax_residencies[] 重复组）与抽取路径（D4：确定性文本/标签抽取 + Vision 双路并行 + 一致性 diff）。规则引擎尚未实现，将与本仓库同仓交付。要求更深而非更大。"

**证据基线**: 本规格的所有需求条目均可回溯到同目录 `mapping-matrix.csv`（48 个字段位 × 9 列，0 空格）。`row_id` 列即回溯键。四份官方 PDF 的 SHA-256 已与 IRD 线上文件比对一致。

## Clarifications

### Session 2026-11-04

- Q: 当实体表单自述的注册成立地与商户底表中 KYC 记录的注册成立地不一致时，系统应当如何处置？ → A: Option B — 并列保留两个来源、各自带来源标记；不一致时记跨源冲突 WARNING → `MANUAL_TRIAGE`，交既有跨源研判环节。理由：表单是持有人签署并承担 s.80(2E) 刑责的法律文件，丢弃自述值等于销毁证据；覆写 KYC 则污染商户底表。
- Q: FR-036 所要求的两条抽取路径，其「独立」的边界在哪里？ → A: Option B — 字段定位与文本归属逻辑必须相互独立；共享层严格限定于文档解密与页面枚举；共享层失败从一致率分母中排除并单独计数。理由：解密与页面枚举不含推理成分，其正确性可由文档指纹与页数独立验证，重复实现两遍是纯成本。
- Q: 实体表与控权人表之间的跨文档链接应使用什么键？ → A: Option C — Ref. No. 为主键，控权人姓名 + 出生日期为兜底印证；两信号不一致或均不可用时降级 `MANUAL_TRIAGE`；任何自动链接带置信度标记，低置信不得视为已确认。理由：Ref. No. 由财务机构自行编派、表单未规定唯一性范围，单独使用会静默产生有法律后果的错误链接；姓名 + DOB 单独使用在同名同姓时同样会错配。
- Q: FR-038 要求不一致时保留双方结果，这使敏感数据留存面翻倍，留存策略应如何收窄？ → A: Option C — 仅不一致的字段位保留双方原值；一致的字段位只保留一路原值加逐字段位一致性标记；加密存储的敏感字段清单扩展至 HK 身份证号 / 护照号、出生日期、出生地。理由：一致字段位保留两份相同原值无裁决价值、只有泄露面；收窄后一致率仍可独立复算，因为复算需要的是一致性标记而非双方原值。
- Q: 映射矩阵中 24 条「严重」缺口应按什么闸门筛选处置？ → A: Option B — 双闸（是否法律须报送 + 是否可确定性校验），处置取四类：纳入数据契约 / 纳入规则配置 / 部分纳入（规则纳入而槽位全展开排除）/ 显式排除转人工；当前分布 19 / 3 / 2 / 0。理由：全纳入违反「更深而非更大」与「不做控权人 8 槽全展开」；只纳入 D3/D4 直接相关的 7 条会使 SC-002（星号字段位 8/8）失败，因为 R06/R07/R14/R16 是星号字段位却不在那 7 条内。

**授权说明**: Q1 由用户明确选择建议项；Q2–Q5 由用户以「按建议执行」授权代决。如需翻转任一项，指明题号即可，对应的 FR 与 SC 将同步回滚。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 受理官方加密表单而不拒收 (Priority: P1)

受理员把客户提交的 IRD 官方自我证明表交给系统。这些 PDF 是 AES-128 加密的（空用户密码）且是带结构树的 Tagged PDF。系统必须在入口就把它们当作合法输入受理，给出裁决结果，而不是以「不支持加密 PDF」为由退回。

**Why this priority**: 这是全链路的第一道闸。当前 PRD §4.2 F1 明文写「不支持加密 PDF」，而 IRD 官方样本本身就是加密的——意味着按现行规格，**HK 这条唯一已落地的法域在入口就 100% 拒收**，后面所有需求都无从谈起。（R47、R48）

**Independent Test**: 单独投放四份官方 PDF（个人版 / 实体版 / 控权人版 / 术语表），断言入口零拒收、每份都产出一个裁决对象。不需要任何其他功能即可验证，且验证通过即代表 HK 法域从「不可用」变为「可用」。

**Acceptance Scenarios**:

1. **Given** 一份 AES-128 加密、空用户密码的 IRD 官方自我证明表，**When** 受理员提交给系统，**Then** 系统受理该文档并产出裁决，不产生「格式不支持」类拒收。
2. **Given** 一份带结构树（含表格行列语义）的 Tagged PDF，**When** 系统抽取其中的表格字段，**Then** 字段与其所属行列的归属关系被保留，不出现跨行串位。
3. **Given** 一份权限位受限（禁止打印/复制）但可阅读的加密 PDF，**When** 系统读取其内容，**Then** 权限位本身不构成拒收理由，且系统不试图绕过任何访问控制之外的限制。
4. **Given** 一份真正损坏或空用户密码无法解开的 PDF，**When** 受理员提交，**Then** 系统给出可区分的、非「加密」归因的失败原因并转人工。

### User Story 2 - 一位持有人有多个税收居民身份 (Priority: P2)

受理员处理一位既是 HK 税收居民、又是另一法域税收居民的持有人。表单原文的 TIN 表是 5 行重复组，且明文标注「Indicate all (not restricted to five) jurisdictions of residence」。系统必须能表达任意个数的税收居民身份，并对每一个法域分别完成必填性、TIN 格式、无 TIN 理由（A/B/C）的裁决。

**Why this priority**: 这是 D3 的核心，也是当前契约最严重的表达力缺陷。现行 `jurisdiction_code` 与 `tin` 都是单值，**在数据模型层面就无法表示「多重税收居民」这一 CRS 的基本事实**——不是校验不严，而是根本存不下。且这两个字段位都是法律要求须报送 IRD 的（表格上加星号）。（R28、R29、R41）

**Independent Test**: 构造一份含 3 个税收居民地的持有人数据（其中 1 个无 TIN、理由为 B 并附解释），断言三条记录全部留存、逐条各自裁决、且无 TIN 的那条不因缺 TIN 被判 BLOCKER。不依赖实体/控权人路径即可验证。

**Acceptance Scenarios**:

1. **Given** 一位持有人在表单 TIN 表中填了 3 个法域，**When** 系统抽取并裁决，**Then** 3 条税收居民记录全部保留，各自带自己的 TIN 或自己的无 TIN 理由。
2. **Given** 一位持有人填了 6 个法域（超出表格印刷的 5 行，按原文允许续页），**When** 系统抽取，**Then** 不因「表格只有 5 行」而截断，6 条全部保留。
3. **Given** 某法域的 TIN 缺失且理由选择 B，**When** 系统裁决该条记录，**Then** 校验该条的解释文本非空且去空白后达到最小可读长度；理由缺失或为 A/C 时不得强制要求解释。
4. **Given** 某法域填了 TIN 同时又填了无 TIN 理由，**When** 系统裁决，**Then** 报出两者互斥的冲突，而不是任选其一静默通过。

### User Story 3 - 表单自带的派生等值规则被自动执行 (Priority: P3)

表单在 Part 3 明文规定：若持有人是 HK 税收居民，其 TIN 即 HK 身份证号（个人 / 控权人）或商业登记号（实体）。这类规则是确定性的、跨字段的、零推理的。系统必须把它们作为独立可执行的校验跑出来，而不是把它们塌缩成同一个字段值后失去校验能力。

**Why this priority**: 这类规则一旦被契约「顺手满足」（两个来源字段塌缩为一个 `tin`），校验就永久消失了——系统再也没办法发现「HK 居民的 TIN 与 HKID 不一致」这种真实的填报错误。它同时是 D4 确定性路径最直接的收益证明：这些检查不需要任何模型推理。（R10、R12、R32、R33、R34）

**Independent Test**: 提交一份 HKID 与 TIN 表中 HK 行 TIN 故意不一致的个人版表单，断言系统报出该等值违规。此测试不依赖 P1 之外的任何抽取能力假设（可用结构化输入直投）。

**Acceptance Scenarios**:

1. **Given** 一份个人版表单，Part 1 的 HKID 与 TIN 表中 HK 行的 TIN 不一致，**When** 系统裁决，**Then** 报出跨字段等值违规，并指出两个来源字段位。
2. **Given** 一份实体版表单，Part 1 的商业登记号与 TIN 表中 HK 行的 TIN 不一致，**When** 系统裁决，**Then** 同样报出等值违规。
3. **Given** 一份实体声明自己不是任何法域的税收居民（例如财政透明体），并填了实际管理地，**When** 系统裁决，**Then** 系统区分「税收居民地」与「实际管理地」两种申报语义，不把后者当作前者的替代品静默接受。
4. **Given** 某法域选用无 TIN 理由 C，**When** 系统裁决，**Then** 校验理由 C 的适用前提（该法域当局不要求披露 TIN）是否成立，而非只校验字段是否填了。

### User Story 4 - 抽取正确性可被证明，而不是被声称 (Priority: P4)

质检负责人需要回答「抽取准确率到底是多少」。当前 PRD §2.2 把「字段抽取准确率 ≥90%」写成 KPI，但**系统里不存在任何能产生这个数字的机制**——没有对照真值，也没有第二路独立结果可比。系统必须对同一文档产出两条独立抽取结果，并自动报告字段级一致率。

**Why this priority**: 这是 D4 的验收面。它把一个不可度量的 KPI 变成可度量的指标，同时提供了本项目一直缺失的**正确性裁判（oracle）**：两路独立方法在同一字段位上是否同意，是不依赖人工标注就能得到的强信号。P4 排在 P3 之后，因为它衡量的是质量而非可用性。（R48，PRD §2.2）

**Independent Test**: 对同一份官方 PDF 跑两路抽取，断言系统输出一个逐字段位的一致 / 不一致清单和一个总一致率数字。不需要任何人工标注数据即可完成。

**Acceptance Scenarios**:

1. **Given** 一份已完成两路抽取的文档，**When** 质检负责人查看结果，**Then** 得到逐字段位的一致 / 不一致标记，以及一个可复算的字段级一致率。
2. **Given** 两路在某字段位结果不一致，**When** 系统裁决，**Then** 该字段位不得静默采信任一路，必须降级为待人工确认并保留双方结果。
3. **Given** 一路抽取失败而另一路成功，**When** 系统汇总，**Then** 一致率的分母按实际参与比对的字段位计算，失败路不被计为「不一致」从而污染指标。
4. **Given** 一份文档中某字段位在表单上标注为「Not compulsory」且两路都未抽到值，**When** 系统比对，**Then** 该字段位记为「双方一致为空」，不记为不一致。

### User Story 5 - 实体分类触发控权人补齐链 (Priority: P5)

受理员处理一份实体版表单。实体在 Part 2 勾选了三分类之一；若勾选 Passive NFE，Part 3 的控权人槽位即为条件必填，且表单明文要求**每位控权人另附一份控权人自我证明表**。控权人版表单又反向列出其所控实体（1–3 个），并在 Part 4 用「11 种控权人类别 × 3 个实体列」的二维矩阵勾选。系统必须把这条跨文档的条件必填链表达出来并裁决。

**Why this priority**: 这是缺口密度最高的一条链（R21/R22/R23/R25/R26/R27 全部为「严重」），但它只在 Passive NFE 分支上生效，属于条件路径而非主干，因此排在 P5。当前契约明文排除了实体三分类，导致这条链在模型层完全不存在。（R21–R27）

**Independent Test**: 提交一份勾选 Passive NFE 但控权人槽位为空的实体表单，断言系统报出条件必填缺失；再提交一份补齐了 2 位控权人但只附了 1 份控权人表的组合，断言系统报出跨文档数量不匹配。

**Acceptance Scenarios**:

1. **Given** 一份实体表单勾选了 Passive NFE 且控权人槽位为空，**When** 系统裁决，**Then** 报出条件必填缺失（BLOCKER 级），并引用触发它的分类结果。
2. **Given** 一份实体表单勾选了 Active NFE，**When** 系统裁决，**Then** 控权人槽位为空是合法的，不得报缺。
3. **Given** 实体表单勾选了三分类中带填空的子项（例如「regularly traded on ___」），**When** 系统抽取，**Then** 该填空被归属到正确的子项，不因线性读取而错位或丢失归属。
4. **Given** 一份实体列出 2 位控权人，**When** 系统检查随附文档，**Then** 要求恰好 2 份控权人表，且每份能回指到该实体；数量或指向不符即报跨文档不一致。
5. **Given** 一份控权人表在 Part 4 对 Entity(1) 勾了 A 类、对 Entity(2) 勾了 B 类，**When** 系统抽取，**Then** 两个实体列的勾选各自独立保留，不被压成一维单值。
6. **Given** 一个合伙形式的实体，**When** 系统应用控权人持股门槛，**Then** 使用与该实体形式和该业务日期匹配的门槛值，而不是一个全局常数。
7. **Given** 实体声明不存在持股或表决权意义上的自然人控制，**When** 系统裁决控权人必填，**Then** 接受「高级管理人员」作为兜底控权人，而不是把空值当作合法。

### Edge Cases

- **一份表单多个持有人**：三份表单的 Part 1 均明文要求联名 / 多持有人账户**每位持有人各填一份**。系统必须把「一份文档 = 一个持有人」作为基数约束，而不是把多人塞进一条记录。（R04）
- **「Not applicable」是合法空值**：表单总则写明「All parts must be completed (unless not applicable or otherwise specified)」。系统不得把标注为不适用或非强制的字段位的空值判为缺失。（R20、R42）
- **续页**：总则写明空间不足时续写于附加页。任何按固定页数上限的抽取都会漏数据。（R43）
- **原文排版缺陷**：个人版 Part 1(4) 邮寄地址块印刷上出现两个「Line 2」。抽取结果必须能暴露这种源文档异常，而不是静默择一。（R18）
- **删除线选项未消解**：个人 / 控权人版声明含「# Delete as appropriate」的二选一。若两选项都保留或都划去，声明本身无效。（R35）
- **实体版签署人必然不是持有人**：实体版声明没有「本人是账户持有人」选项，因此签署人 Capacity 在实体路径上恒为必填。（R36）
- **签署人姓名与持有人姓名不一致**：此时 Capacity 必填；以授权书签署的还须附证明副本。（R38、R39）
- **监管参数会过期**：控权人门槛脚注明文「With effect from 1 January 2021」为 25%（法团）/ 0%（合伙）；警告区的第三级罚款金额 $10,000 硬印在表单上，而 2025-12-09 启动的公开咨询已提议提高罚则。此类参数必须带生效日期且不得硬编码在代码或契约里。（R27、R45、R46）
- **合伙 0% 门槛的语义**：0% 意味着每一位合伙人都是控权人，而不是「无人达标」。（R27）
- **30 天变更通知义务**：声明区承诺情形变更后 30 天内提供更新表格。这是「有理由知道」重新取证逻辑的期限依据。（R44、R45）

## Requirements *(mandatory)*

### Functional Requirements

**文档受理**

- **FR-001**: 系统 MUST 受理 IRD 官方发布的自我证明表 PDF，包括以空用户密码加密的文档；文档加密属性 MUST NOT 单独构成拒收理由。（R47）
- **FR-002**: 系统 MUST 在无法解密或文档损坏时给出与「加密」可区分的失败归因，并将该文档转人工。（R47）
- **FR-003**: 系统 MUST 保留 Tagged PDF 结构树所提供的表格行列归属信息；当结构树不可用时 MUST 记录该降级事实，使下游知道字段归属的可信度下降。（R48）
- **FR-004**: 系统 MUST 支持续页，不得以固定页数上限截断抽取。（R43）
- **FR-005**: 系统 MUST 强制「一份文档对应一个持有人」的基数；多持有人账户 MUST 要求多份文档。（R04）

**身份与地址**

- **FR-006**: 系统 MUST 分别保留姓名的组成部分（称谓、姓、名、中间名），不得只存一个合并后的全名字符串；对实体 MUST 保留其法定名称，且 MUST 能区分该名称属于实体本身还是其分行——两者在申报上是不同的账户持有人。（R05–R09）
- **FR-007**: 对于法律要求须报送的姓名字段位（姓、名），系统 MUST 判为 BLOCKER 级缺失而非 WARNING。（R06、R07、R41）
- **FR-008**: 系统 MUST 以结构化方式保留地址（街道行、城市、省/州、国家、邮编），使国家码可被独立校验；不得只存一个拼接后的地址字符串。（R13、R14、R15、R16、R17）
- **FR-009**: 对于法律要求须报送的地址字段位（城市、国家），系统 MUST 判为 BLOCKER 级缺失。（R14、R16、R41）
- **FR-010**: 系统 MUST 区分现居/营业地址与邮寄地址两种地址类型，并支持「仅当两者不同时填写」的条件必填。（R18）
- **FR-011**: 系统 MUST NOT 因出生地未填而判缺失——该字段位在原文标注为「Not compulsory」。（R20、R42）
- **FR-012**: 系统 MUST 把 dd/mm/yyyy 形式的日期转换为无歧义的标准日期表示，并对转换失败给出归因。（R19、R40）

**税收居民身份（D3 核心）**

- **FR-013**: 系统 MUST 以可重复组的形式表达税收居民身份，每组包含：法域、TIN、无 TIN 理由（A/B/C）、理由 B 的解释文本。基数下限 MUST 为 1；表单原文未设上限（「not restricted to five」），但已发布接口对请求体设有 1 MiB 硬上限，故实际上限 MUST 由该传输约束推导并显式记录，MUST NOT 声明为无限。（R28–R31）
- **FR-014**: 系统 MUST 对每一条税收居民记录独立执行必填性、TIN 格式、无 TIN 理由有效性的裁决。（R28–R31）
- **FR-015**: 系统 MUST 校验 TIN 与无 TIN 理由互斥；两者同时存在 MUST 报冲突。（R29、R30）
- **FR-016**: 系统 MUST 并列保留两个来源的注册成立地——表单自述值与商户底表 KYC 值——各自带来源标记，二者 MUST NOT 互相覆写；不一致时 MUST 记为跨源冲突 WARNING 并导向 `MANUAL_TRIAGE`，交由既有的跨源冲突研判环节处置。（R11）
- **FR-017**: 系统 MUST 区分「税收居民地」与「实际管理地」两种申报语义；当实体声明不属于任何法域税收居民时，MUST 接受实际管理地作为独立的申报事实而非居民地的替代值。（R33）
- **FR-018**: 系统 MUST 执行 HK 派生等值规则：若税收居民地包含 HK，则个人的 TIN MUST 等于其 HK 身份证号，实体的 TIN MUST 等于其商业登记号。违反 MUST 报出，且报告 MUST 指明两个来源字段位。（R10、R12、R32）
- **FR-019**: 系统 MUST 为支撑 FR-018 而分别保留 HK 身份证号 / 护照号与商业登记号这两个来源字段位，不得把它们与 TIN 塌缩为同一存储。（R10、R12、R32）
- **FR-020**: 无 TIN 理由 C 的跨法域适用前提（该法域当局不要求披露 TIN）MUST NOT 由系统自动判定——既有规则引擎已明确「只检查豁免声明完整性，适用性需要人工复核，不会凭无 TIN 声明自动通过」。系统 MUST 保留该人工复核路径，并 MUST 在输出中显式标记「适用性未核实」而非沉默。（R34）

**实体分类与控权人**

- **FR-021**: 系统 MUST 表达实体的三分类（财务机构 / 主动非财务实体 / 被动非财务实体），并 MUST 校验恰好命中一类。（R21）
- **FR-022**: 系统 MUST 保留三分类下带填空的子项，并把填空值归属到正确的子项。（R22）
- **FR-023**: 系统 MUST 执行条件必填：实体分类为被动非财务实体 ⟹ 控权人槽位至少 1 个。（R23）
- **FR-024**: 系统 MUST 在实体声明无自然人控制时，接受「高级管理人员」作为兜底控权人，MUST NOT 把空值视为合法。（R24）
- **FR-025**: 系统 MUST 校验跨文档一致性：实体列出的每位控权人 MUST 有一份对应的控权人表，且该表 MUST 能回指该实体。（R23、R25）
- **FR-026**: 系统 MUST 以二维方式保留控权人类型矩阵（控权人类别 × 所控实体），MUST NOT 压成一维单值。（R26）
- **FR-027**: 系统 MUST 支持控权人表反向列出 1–3 个所控实体，并逐个校验回指关系。（R25）
- **FR-028**: 控权人持股 / 表决权门槛 MUST 作为带生效日期的监管参数按实体形式取值（法团与合伙不同），MUST NOT 硬编码为常数。（R27）

**签署与声明**

- **FR-029**: 系统 MUST 校验「本人是账户持有人 / 本人获授权代签」二选一已被消解；未消解 MUST 判定声明无效。（R35）
- **FR-030**: 在实体路径上，系统 MUST 把签署人 Capacity 判为必填。（R36）
- **FR-031**: 系统 MUST 比对签署人姓名与持有人姓名；不一致时 Capacity MUST 必填，且若以授权书签署 MUST 要求附证明副本。（R38、R39）
- **FR-032**: 系统 MUST 校验签署日期不晚于裁决当日；并 MUST 记录签名是否存在（存在性由上游判定，本系统不验笔迹）。（R37、R40）

**缺口处置与严重度**

- **FR-033**: 系统 MUST 依据表单上的星号标记（该标记的含义是「须由申报财务机构报送 IRD」）来区分字段位缺失的严重度：星号字段位缺失 MUST 记为 BLOCKER，非星号字段位缺失 MAY 记为 WARNING。二者沿用既有裁决词汇——BLOCKER 导向 `NEED_USER_FIX`，仅有 WARNING 导向 `MANUAL_TRIAGE`。（R41）
- **FR-034**: 映射矩阵中判定为「严重」缺口的 24 个字段位 MUST 各有一个明确处置，取值限于四类：纳入数据契约、纳入规则配置、部分纳入（规则纳入而槽位全展开排除）、显式排除转人工。MUST NOT 存在无处置的严重缺口。筛选闸门为「是否法律须报送」与「是否可确定性校验」双闸；当前处置分布为 19 / 3 / 2 / 0，逐项清单见 plan.md。处置结果 MUST 复用既有接口已提供的 `verification_level` 与「已执行 / 未执行检查」输出机制来表达，MUST NOT 新造一套并行的披露格式。（R04–R48 中 24 条「严重」）
- **FR-035**: 系统 MUST 把「不适用」与「非强制」视为合法空值来源，MUST NOT 据此判缺失。（R20、R42）

**抽取质量可证明性（D4 核心）**

- **FR-036**: 系统 MUST 对同一文档产出两条抽取结果，二者 MUST 在字段定位与文本归属逻辑上相互独立；共享层 MUST 严格限定于文档解密与页面枚举——这两步不含推理成分，其正确性可由文档指纹与页数独立验证。（R48）
- **FR-037**: 系统 MUST 输出一个可复算的字段级一致率，其分子分母定义 MUST 明确记录，使第三方可独立重算；源自共享层（解密 / 页面枚举）的失败 MUST 从分母中排除并单独计数，MUST NOT 计为「一致」。（PRD §2.2、R47）
- **FR-038**: 两路结果不一致的字段位 MUST NOT 静默采信任一路，MUST 降级为待人工确认并同时保留双方原值；一致的字段位 MUST 只保留一路原值加逐字段位一致性标记，使一致率仍可独立复算而不重复留存敏感数据。（R48）
- **FR-039**: 一路失败时，一致率的分母 MUST 按实际参与比对的字段位计算，失败路 MUST NOT 计为不一致。（FR-037）
- **FR-040**: 「双方一致为空」MUST 记为一致，MUST NOT 记为不一致。（R20、R42）

**监管参数与法域扩展**

- **FR-041**: 所有监管参数（控权人门槛、变更通知期限、罚则金额与级别）MUST 带生效日期，且 MUST 存放于外部规则配置而非代码或数据契约中。三处来源对「外部规则配置」的载体说法不一致——ADR-003 与 `specs/data-spec.md` §3 指 JSON 文件、`AGENTS.md` Guardrails 亦指 `rules/` JSON，而 `assets/crs-templates/API_INTEGRATION.md:15,160` 指「数据库发布活动规则」并以 `rule_revision` / `rule_version_id` 返回。载体 MUST 由团队裁定为单一来源；本规格只约束「不得在代码或数据契约中硬编码」这一不变量。（R27、R45、R46）
- **FR-042**: 未配置的法域 MUST 走 `MANUAL_TRIAGE`（记 WARNING 而非 BLOCKER，推送合规官），MUST NOT 以默认值静默通过、也 MUST NOT 直接判 `NEED_USER_FIX`。CN / SG 在本轮维持未配置。
- **FR-043**: 系统 MUST 暴露源文档自身的异常（例如原文排版重复的字段标签），MUST NOT 静默择一。（R18）

**文档头与跨文档链接键**

- **FR-044**: 系统 MUST 保留文档头的收件财务机构名称与地址，用于确认该表单确实是提交给本机构的。（R01、R02）
- **FR-045**: 系统 MUST 保留文档头的机构参考号（Ref. No.）。实体表与控权人表之间的跨文档链接 MUST 以 Ref. No. 为主键、以控权人姓名 + 出生日期为兜底印证，以支撑 FR-025 与 FR-027；两个信号不一致或均不可用时 MUST 降级为 `MANUAL_TRIAGE`。任何自动建立的链接 MUST 带置信度标记，低置信 MUST NOT 被当作已确认。（R03）

**敏感数据保护**

- **FR-046**: 加密存储的敏感字段清单 MUST 扩展至覆盖 HK 身份证号 / 护照号、出生日期与出生地，不限于既有的 TIN 与商户信息；此扩展是 FR-038 保留双方原值所引入的额外留存面的对冲措施。（R10、R19、R20；PRD §4.2 存储加密行）

### Key Entities *(include if feature involves data)*

- **自我证明文档**：一次受理的最小单位。属性：文档类型（个人 / 实体 / 控权人 / 术语表）、是否加密、结构树是否可用、页数与是否含续页、文档指纹。基数约束：一份文档 = 一个持有人。（R04、R47、R48、R43）
- **账户持有人**：个人与实体的共同抽象。个人分支持姓名组成部分、出生日期、出生地、HK 身份证/护照号；实体分支持法定名称、注册成立地、商业登记号、实体分类。（R05–R22）
- **姓名组成部分**：称谓、姓、名、中间名。姓与名为须报送字段位。（R05–R08）
- **结构化地址**：街道行、城市、省/州、国家、邮编，加地址类型（现居/营业 或 邮寄）。（R13–R18）
- **税收居民身份**：可重复组。属性：法域、TIN、无 TIN 理由（A/B/C）、理由 B 解释。这是 D3 修订的核心实体，取代原单值 `jurisdiction_code` + `tin`。（R28–R31）
- **实体分类**：三分类结果 + 命中子项 + 子项填空值及其归属。（R21、R22）
- **控权人关联**：跨文档外键。属性：控权人身份、其所控实体（1–3 个）、二维类型矩阵（控权人类别 × 实体列）。（R23、R25、R26）
- **签署声明**：二选一消解结果、签署人姓名、Capacity、签署日期、是否授权书签署。（R35–R40）
- **监管参数**：带生效日期的取值集合（控权人门槛按实体形式、变更通知期限、罚则级别与金额）。存放于外部规则配置。（R27、R45、R46）
- **抽取证据**：逐字段位的两路结果、一致性标记、参与比对的字段位集合，以及由此复算出的字段级一致率。（FR-036–FR-040）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 四份 IRD 官方 HK 样本 PDF 在入口的拒收数为 0（当前规格下为 4/4，因「不支持加密 PDF」）。
- **SC-002**: 数据契约可表达的法律须报送字段位（表单星号标记）数量为 8/8（当前为 2/8）。
- **SC-003**: 映射矩阵中 24 条「严重」缺口全部具备明确处置记录，分布为「纳入数据契约 19 / 纳入规则配置 3 / 部分纳入 2 / 显式排除 0」，无处置的严重缺口数为 0。
- **SC-004**: 字段级一致率可被系统自动输出且第三方可独立复算（当前该指标不存在，PRD §2.2 的 ≥90% 无产生机制）。
- **SC-005**: 3 条派生等值规则（个人 HK TIN=HKID、实体 HK TIN=商业登记号、税收居民地与实际管理地语义区分）各有 1 条对应的可执行校验，覆盖 3/3。
- **SC-006**: 同一份表单在业务日期 2020-12-31 与 2021-01-01 下，对同一合伙实体的控权人判定结果 MUST 不同（证明监管参数的生效日期真实生效，而非被常数替代）。
- **SC-007**: 一位持 3 个税收居民地的持有人，其 3 条记录在裁决后的留存数为 3/3，且每条各自带独立的裁决结论（当前单值契约下为 1/3）。
- **SC-008**: 一份列出 2 位控权人的被动非财务实体，在只随附 1 份控权人表时 MUST 被检出跨文档不一致（当前契约下该链不存在，检出数为 0）。
- **SC-009**: 一致率的分母中，源自共享层（解密 / 页面枚举）失败而被计入「一致」的字段位数为 0——共享层失败 MUST 单独计数。这是 SC-004 的反作弊闸：若共享层失败被算作一致，一致率会系统性虚高。
- **SC-010**: 自动建立的实体 ↔ 控权人链接 100% 带置信度标记（0 条无标记），且低于阈值而被降级为 `MANUAL_TRIAGE` 的链接数可被单独报告。

## Assumptions

- **官方样本是 L1 证据，不是契约真源（L0）**。IRD 明文允许各申报财务机构自行设计自我证明表，只要求「必须收集到规定数据」。因此这三份 PDF 的效力是：HK 法域的字段清单来源、版式参考、演示素材。契约的真源是《税务条例》(Cap. 112) 附表 17D（尽职审查）、第 80(2E) 条（罚则）与 OECD CRS XML Schema。
- **OECD CRS XML Schema 的具体元素名未经核实**。本环境中 oecd.org 返回 HTTP 403，无法取得权威 XSD。因此 `mapping-matrix.csv` 中的 `crs_xsd_element__UNVERIFIED` 整列均为待人工核实项，MUST NOT 被当作事实写入任何下游实现或对外契约。
- **HK 是当前唯一已配置法域**。CN / SG 维持未配置，按 FR-042 走 `MANUAL_TRIAGE`；本规格不做法域扩展。
- **严重度词汇沿用既有定义**：`specs/data-spec.md` §1.3 已定义 `AUTO_PASS`（无 BLOCKER 无 WARNING）/ `NEED_USER_FIX`（存在 BLOCKER，生成修复卡片）/ `MANUAL_TRIAGE`（仅 WARNING，推送合规官）。本规格的 BLOCKER / WARNING 分级直接映射到这三个既有裁决值，不新造词汇。
- **规则文件目前不存在，且载体存在三方分歧**。`specs/data-spec.md` §3 声明数据来源为 `rules/rules_v1_base.json` 与 `rules/rules_v2_patch.json`，但 `rules/` 目录为空；同时 `API_INTEGRATION.md:15` 要求「先配置数据库并发布活动规则」，`NO_ACTIVE_RULES` 为 503 错误码，响应返回 `rule_revision` 与 `rule_version_id`，并提及「global v4 规则」。FR-041 因此是新建而非修订。有利的一面是 §3 的 `.algorithm` 枚举已包含 `HKID_WEIGHT`，正是 FR-018 所需的算法位；不利的一面是 §3 的结构只有 `{法域: {正则, 算法}}`，仅能承载本规格识别出的 27 个确定性监管参数中的 3 个（见 plan.md 的 M/N 表达力测算）。
- **本轮识别的缺口，多数已被规则引擎作者自行记录**。`assets/crs-templates/API_INTEGRATION.md:168-170`「当前接入边界」已明文承认：一次请求只支持一个税收居民地区而两份 PDF 均支持多地区；实体分类、控权人、邮寄地址、出生地、授权签署人尚未纳入请求契约；实体成立日期缺失时无法仅凭该 PDF 构造完整请求。`README.md:14` 与 `README.md:27` 亦自相矛盾（前者称表格支持多地区，后者称接口一次只支持一个）。因此本规格的贡献不是「发现」这些缺口，而是：量化到 48 个字段位、给出逐行可回溯的映射矩阵、并为已被承认的边界提供修订方案与处置清单。
- **已发布接口对未知字段零容忍**。`API_INTEGRATION.md:97` 明文「顶层和 form_data 不接受未知字段」。因此 D3 引入 `tax_residencies[]` 是一次**破坏性契约变更**而非新增可选字段，变更单 MUST 同时给出迁移方式；请求体另有 1 MiB 硬上限（`:158` 的 413 `REQUEST_TOO_LARGE`），构成 FR-013 的实际基数上界。
- **`specs/data-spec.md` §1.1 与实际接口不一致**。请求示例含 13 个字段，§1.1 只记录 10 个，缺 `holder_type`（INDIVIDUAL / ENTITY）与 `tin_type`（HKID / HK_BR）。其中 `tin_type` 正是 R32 派生等值规则的半个锚点——类型标记被留存了，来源值却被塌缩进单一 `tin`，因此等值校验仍无法执行。顶层另有 `policy.today`（业务日期，由主后端传入，非 PDF 抽取字段）与 `indicia_issues[]`（上游跨源核查问题），二者是 FR-032 与 SC-006 的既有输入。
- **`backend/` 目前只有脚手架**：健康检查路由、配置、日志、数据库连接、异常基类、模型与仓储基类、用户模型。不存在任何 CRS 领域模型、校验服务或裁决器。因此本规格的全部 FR 均为新建，plan.md MUST NOT 假设存在可修改的实现落点。
- **本规格不包含 CRS XML 报文的生成**，也不包含 CARF / 加密资产申报。2025-12-09 启动、2026-02-06 截止的公开咨询（CARF 自 2028 年、修订版 CRS 自 2029 年起实施，并提议强制财务机构登记与提高罚则）只作为「监管参数不得硬编码」这一要求的理由被引用，不作为本轮实现范围。
- **规则引擎尚未实现，将与本仓库同仓交付**。因此 FR-041 所要求的「外部规则配置」在本仓库内有唯一落点，不存在跨仓协调成本；同时这也意味着现行 `specs/data-spec.md` §3 的规则配置结构与引擎侧结构之间的分歧必须在同一轮内解决，而非推给另一个团队。
- **`assets/crs-templates/` 内的四份 PDF 已与 IRD 线上文件做 SHA-256 比对一致**，两次独立下载结果稳定，可作为可复现证据基线。
- **签名真实性不在范围内**。系统只判签名是否存在（由上游判定），不验笔迹。
- **本轮不产出实现代码、不修改 `specs/` `design/` `docs/`、不提交 git**。对上述 PM-owned 文档的修订以「变更单」形式交付，由 PM 裁决后落地。
